# Резервное копирование и восстановление

3-2-1, RPO/RTO, инкремент, проверка
### Резервное копирование и восстановление

Бэкап нужен не «на всякий случай», а чтобы гарантированно **восстановить данные и работу** после сбоя, ошибки или атаки (в т.ч. шифровальщика).

### Ключевые метрики

| Метрика | Смысл                                             |
| ------- | ------------------------------------------------- |
| RPO     | сколько данных допустимо потерять (частота бэкапа) |
| RTO     | за какое время нужно восстановить работу           |
| Retention | срок хранения копий                             |

Чем меньше RPO/RTO, тем дороже решение — их согласуют с бизнесом.

### Правило 3-2-1

- **3** копии данных;
- **2** разных носителя/технологии;
- **1** копия **вне площадки** (offsite) — защита от пожара/шифровальщика.

Плюс: хотя бы одна копия **immutable/offline** — чтобы её нельзя было зашифровать из сети.

### Виды бэкапов

| Вид          | Что копирует                    | Плюсы/минусы           |
| ------------ | ------------------------------- | ---------------------- |
| Полный (full)| всё                            | просто восстановить, долго/много места |
| Инкрементный | изменения с прошлого бэкапа     | быстро, восстановление из цепочки |
| Дифференциальный | изменения с последнего полного | компромисс             |
| Снапшот      | состояние тома на момент        | быстро, но не бэкап сам по себе |

### Стратегии и инструменты

- **Linux**: `rsync`, `tar`, `restic`/`borg` (дедупликация, шифрование), `dump`;
- **Windows**: `wbadmin`, VSS (теневые копии), Backup and Restore;
- **VM**: бэкап на уровне гипервизора (Proxmox Backup Server, Veeam) — образ ВМ целиком;
- **БД**: логический дамп (`pg_dump`/`mysqldump`) + WAL/binlog для point-in-time recovery;
- **расписание**: `cron`/systemd timer/Task Scheduler.

### Проверка и восстановление

Бэкап без проверки восстановления — не бэкап:

- регулярно выполнять **тестовое восстановление** на отдельный узел;
- контролировать `retention` и целостность (`restic check`, контрольные суммы);
- вести журнал: что, когда, куда, результат;
- хранить копии **отдельно** от продакшена (учётные данные не должны давать доступ к бэкапу).

### Типичные ошибки на экзамене:

- бэкап на том же диске/сервере — сбой уничтожает и данные, и копию;
- нет offsite/immutable — шифровальщик шифрует и бэкапы;
- никогда не проверяли восстановление — «бэкап есть, а не поднимается»;
- бэкап «горячей» БД без согласованности (нужен VSS/логи);
- слишком редкий бэкап при жёстком RPO — теряют важные данные;
- забыли про срок хранения — место кончилось, бэкапы перестали идти;
- права на хранилище бэкапов у всего отдела — кто угодно удалит копии;
- путают снапшот ВМ и полноценный бэкап.
