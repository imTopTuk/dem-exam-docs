# ITSM и обработка инцидентов

тикеты, SLA/SLO, приоритеты, база знаний
### ITSM и обработка инцидентов

**ITSM** — управление ИТ-услугами по процессам (ITIL): пользователь получает **услугу**, а не просто «железо». Ключевые процессы: управление инцидентами, запросами, изменениями, проблемами и конфигурациями (CMDB).

### Инцидент vs запрос vs проблема

| Тип       | Что это                              | Цель                     |
| --------- | ------------------------------------ | ------------------------ |
| Инцидент  | незапланированный сбой/деградация    | восстановить услугу быстро |
| Запрос    | стандартная просьба (доступ, ПО)     | выполнить по регламенту  |
| Проблема  | причина одного или серии инцидентов  | устранить **первопричину** |
| Изменение | правка инфраструктуры                | внести контролируемо     |

### Приоритет и SLA

**Приоритет = влияние × срочность** (матрица). От него зависят сроки реакции и решения.

| Уровень | Пример                        | Реакция   |
| ------- | ----------------------------- | --------- |
| P1/критич.| лежит вся сеть офиса         | минуты    |
| P2/высокий | не работает ключевой сервис | < 1 часа  |
| P3/средний | тормозит у части пользователей | день   |
| P4/низкий  | косметика, вопросы          | по плану  |

- **SLA** — договорные сроки с заказчиком; **SLO** — внутренняя цель; **OLA** — договорённости между командами;
- нарушение SLA фиксируют и разбирают на пост-мортеме.

### Жизненный цикл тикета

1. регистрация (кто, что, когда, как воспроизвести);
2. классификация и приоритет;
3. диагностика и **эскалация** (1-я линия → 2-я → вендор);
4. решение и **закрытие с подтверждением** пользователя;
5. запись в **базу знаний (KB)** — чтобы решать быстрее в следующий раз.

### Инструменты и метрики

- **Helpdesk/Service Desk**: GLPI, Jira Service Management, Redmine, Naumen;
- **база знаний** — статьи, чек-листы, типовые решения;
- метрики: время реакции/решения, доля решённых на 1-й линии (FSR), повторные обращения, CSI (удовлетворённость).

### Типичные ошибки на экзамене:

- «чинят» инцидент молча, без регистрации — нет истории и статистики;
- путают инцидент и проблему: тушат симптом, причина остаётся;
- занижают приоритет, чтобы не нарушить SLA — риск пропустить реальную аварию;
- изменения вносят без процесса Change — неожиданные сбои;
- нет обратной связи с пользователем — закрывают «в одностороннем порядке»;
- не ведут KB — одни и те же проблемы решают заново;
- эскалация задерживается из-за гордости 1-й линии;
- SLA есть, но никто его не измеряет.
