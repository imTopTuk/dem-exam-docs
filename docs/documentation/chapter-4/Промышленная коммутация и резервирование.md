# Промышленная коммутация и резервирование

MRP/RSTP, кольца, магистрали, multicast
### Промышленная коммутация и резервирование

Остановка линии из-за обрыва кабеля недопустима, поэтому промышленные сети строят с **резервированием** и быстрым восстановлением.

### Кольцевые протоколы

| Протокол | Восстановление | Особенность                       |
| -------- | -------------- | --------------------------------- |
| STP/RSTP (802.1D/802.1w) | секунды | универсально, но медленно для цеха |
| **MRP** (Media Redundancy Protocol) | **десятки–сотни мс** | стандарт PROFINET-среды          |
| PRP/HSR (802.1CB) | без разрыва (0 мс) | двойной путь, дороже             |
| DLR (EtherNet/IP) | быстро | кольцо в среде Rockwell          |

**MRP**: один коммутатор — **менеджер** кольца, он блокирует резервный сегмент; при обрыве открывает его. Время сходимости — миллисекунды.

### Топологии

- **кольцо** — резервирование линии;
- **магистраль/шинная (daisy-chain)** — дёшево, но один обрыв рвёт всё;
- **звезда** — через коммутатор, точка концентрации;
- **комбинированная** — на практике: кольца на линии + звезда в шкафу.

### Multicast и IGMP

Переменные процесса транслируются **multicast**-ом (не unicast/не broadcast). Чтобы коммутатор не «заливал» multicast во все порты:

- включён **IGMP snooping** — рассылка только подписчикам;
- **IGMP querier** (или static multicast) в кольце/сети;
- при неправильной настройке multicast «штормит» сеть.

### Управляемость

- **VLAN** для разделения зон, **приоритеты (QoS/PCP)** для real-time;
- **порт-мироринг** и **диагностика** (LLDP, топология, устройство-диагностика);
- **storm control** против широковещательных штормов;
- SNMP/веб-интерфейсы для наблюдения (см. мониторинг).

### Типичные ошибки на экзамене:

- на магистрали АСУ ТП стоят **неуправляемые** коммутаторы — нет резервирования/QoS;
- RSTP оставляют в сети hard-RT — сходимость не успевает за требованием;
- кольцо собрано, но **менеджер/резервный сегмент** настроен с ошибкой — нет резерва;
- IGMP snooping выключен — multicast «лавиной» забивает сеть;
- смешивают кольца разных вендоров без проверки совместимости;
- приоритеты QoS не выставлены — real-time-трафик ждёт в очереди;
- «штормовое» поведение не ограничено (нет storm control);
- нет документации по топологии — при обрыве неясно, где искать.
