# Туннелирование тема

Настройка GRE-туннелей, инкапсуляция трафика
### Туннелирование

Туннелирование — способ передать пакет одного протокола внутри пакета другого. Исходный пакет целиком упаковывается в новый (**инкапсулируется**), и поверх сети-транспорта строится логический канал между двумя точками.

```
+-------------------+---------------------+---------------+----------+
| Outer IP header   | Tunnel header (GRE) | Inner IP hdr  | Payload  |
+-------------------+---------------------+---------------+----------+
   доставка между    идентификация         исходный       данные
   конечными точками туннеля              пакет
```

Зачем нужно:

- соединить удалённые сети через публичную сеть (overlay поверх интернета);
- передать **не-IP** или **multicast/broadcast** трафик через IP (например, OSPF между площадками);
- объединить разнородные сети в «одну плоскую»;
- спрятать внутреннюю адресацию от промежуточной сети.

### GRE (Generic Routing Encapsulation)

GRE — простой протокол инкапсуляции. Внутри протокола IP ему соответствует **IP protocol number 47**. Заголовок GRE — от **4 байт** (плюс опциональные поля). GRE **не шифрует** и не аутентифицирует трафик — для защиты его оборачивают в IPsec (**GRE over IPsec**).

#### Оверхед и MTU

Инкапсуляция «съедает» часть MTU:

| Компонент             | Размер |
| --------------------- | ------ |
| Внешний IP-заголовок   | 20 байт |
| GRE-заголовок          | 4 байта |
| **Итого оверхед**      | **24 байта** |

MTU 1500 → полезный MTU туннеля 1476. Если не скорректировать MSS/MTU, крупные пакеты будут теряться (сервис «висит», но `ping` работает).

<span style="color: 00cc18">Ключевые команды (Cisco):</span>

- `interface tunnel0` — создать интерфейс туннеля;
- `tunnel source gi0/0` (или IP) и `tunnel destination <IP>` — концы туннеля, должны быть достижимы;
- `tunnel mode gre ip` — режим (по умолчанию);
- `ip address 10.255.0.1 255.255.255.252` — адрес внутри туннеля;
- `ip mtu 1476` и `ip tcp adjust-mss 1436` — борьба с фрагментацией;
- `keepalive` — контроль живости туннеля;
- проверка: `show interface tunnel0`, `show ip route`.

<span style="color: 00cc18">Linux / FRR:</span>

- `ip tunnel add gre1 mode gre local 203.0.113.1 remote 203.0.113.2 ttl 255`;
- `ip addr add 10.255.0.1/30 dev gre1`; `ip link set gre1 up`;
- в FRR туннель настраивают на уровне ОС, а маршруты/OSPF — в `vtysh`.

<span style="color: 00cc18">MikroTik:</span>

- `/interface gre add name=gre1 remote-address=203.0.113.2 local-address=203.0.113.1`;
- `/ip address add address=10.255.0.1/30 interface=gre1`.

#### GRE over IPsec

Схема «сначала туннель, потом шифрование»: GRE остаётся простым и умеет multicast (нужен для OSPF), а IPsec в transport-режиме шифрует уже GRE-пакеты. Так получают одновременно маршрутизацию между площадками и защиту трафика.

#### Типичные ошибки на экзамене:

- `tunnel destination` недостижим — интерфейс туннеля поднимается, но трафик не идёт;
- смотрят на `tunnel source/destination` только по IP, забывая про маршрут до них (нужен маршрут до внешних адресов);
- не учли оверхед 24 байта: крупные пакеты фрагментируются или теряются («ping проходит, а сервис нет») — нужно `ip mtu`/`adjust-mss`;
- ждут от GRE шифрования — его там нет, нужен IPsec;
- адреса внутри туннеля пересекаются с адресами физической сети — асимметричная маршрутизация;
- OSPF через GRE не поднимается, потому что multicast не пробрасывается без правильного режима туннеля;
- keepalive выключен — «мёртвый» туннель остаётся в таблице и перехватывает трафик.
