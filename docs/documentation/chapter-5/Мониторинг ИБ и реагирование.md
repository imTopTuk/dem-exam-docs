# Мониторинг ИБ и реагирование

IDS/IPS, SIEM, журналы, инциденты
### Мониторинг ИБ и реагирование

Безопасность — это процесс: мало «поставить», нужно **видеть** события и **реагировать** на инциденты. Основа — централизованные журналы и корреляция событий.

### Средства мониторинга

| Класс | Назначение                       | Примеры              |
| ----- | -------------------------------- | -------------------- |
| IDS   | обнаружение вторжений (пассивно)  | Snort, Suricata      |
| IPS   | обнаружение и блокировка          | Suricata (inline), NGFW |
| HIDS  | контроль узла (файлы, процессы)   | OSSEC, Wazuh, AIDE   |
| SIEM  | сбор/корреляция логов, алерты      | Wazuh, MaxPatrol SIEM |
| DLP   | защита от утечек данных           | —                    |
| сканер уязвимостей | поиск слабостей       | OpenVAS, MaxPatrol VM |

### Мониторинг и журналы

- собирать журналы **со всех узлов** (Linux/Windows/оборудование/АСУ ТП);
- синхронизация времени (NTP) — обязательна для корреляции;
- **корреляция**: несколько событий → инцидент (например, много `failed password` + успешный вход);
- мониторить целостность файлов (AIDE), конфигурации, изменения прав;
- алерты на аномалии: новый admin, отключение аудита, скачивание баз, обращение к honeypot.

### Реагирование на инциденты

Цикл (NIST): **подготовка → обнаружение/анализ → сдерживание → устранение → восстановление → выводы (post-mortem)**.

- зафиксировать и **сохранить доказательства** (образы, логи) до «зачистки»;
- локализовать (изолировать узел, заблокировать учётку/адрес);
- уведомить ответственных и, при необходимости, регулятора;
- устранить причину, восстановить из чистых бэкапов;
- разобрать и обновить правила/регламенты.

### Типичные ошибки на экзамене:

- логи есть, но никто их не смотрит — нет алертов и корреляции;
- разное время на узлах — события нельзя сопоставить;
- во время инцидента **сразу чистят** заражённую машину, теряя доказательства;
- IDS установлен, но не обновляются сигнатуры;
- SIEM настроен без приоритетов — «шум», реальное событие тонет;
- нет регламента и ответственного — реагируют хаотично;
- восстановление из заражённого/старого бэкапа;
- не проводят пост-мортем — инцидент повторяется.
